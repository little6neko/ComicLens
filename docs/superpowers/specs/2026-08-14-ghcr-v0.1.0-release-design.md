# GHCR 多架构镜像与 v0.1.0 发布设计

## 目标

为 ComicLens 建立与 FileButler 发布流程一致的容器镜像发布能力，并完成首个 `v0.1.0` 版本发布：

- 仅在推送符合 `v*.*.*` 的 Git 标签时触发 GitHub Actions；
- 将镜像发布到 `ghcr.io/little6neko/comiclens`；
- 同时提供 `linux/amd64` 和 `linux/arm64` 镜像；
- 发布不可变版本标签 `v0.1.0`，并让 `latest` 指向同一版本；
- 将应用可见版本和镜像元数据统一为 `0.1.0`；
- 在 README 中提供可直接复制的 Docker 安装、密码配置、持久化、日志和升级说明。

参考实现为 FileButler 的 [镜像发布 workflow](https://github.com/little6neko/FileButler/blob/main/.github/workflows/publish-image.yml) 和 [v0.1.5 发布提交](https://github.com/little6neko/FileButler/commit/d2112d0dd54e40640b50cd619ae4e1087628b692)。

## 已确认方案

采用单一 GHCR 发布方案：

- 不发布 Docker Hub 镜像；
- 普通 `main` 分支推送不构建发布镜像；
- 使用轻量 Git 标签触发发布；
- 保留现有 `docker-compose.yml` 作为从当前源码构建的本地部署方式；
- 本次不新增指向 GHCR 的 release compose 文件。

这样可以避免同一版本存在多套发布入口，同时仍保留开发者从源码构建和调试的能力。

## GitHub Actions 工作流

新增 `.github/workflows/publish-image.yml`，工作流名为 `Publish Docker image`。

### 触发条件

工作流仅监听：

```yaml
on:
  push:
    tags:
      - "v*.*.*"
```

因此提交或推送 `main` 本身不会发布镜像。推送 `v0.1.0` 标签后才会开始构建。

### 权限与认证

Job 只申请发布所需权限：

- `contents: read`：检出仓库；
- `packages: write`：向当前仓库所有者的 GHCR 包写入镜像。

工作流使用 GitHub 自动提供的 `GITHUB_TOKEN` 登录 `ghcr.io`，不要求新增长期访问令牌或仓库 Secret。

### 构建流程

工作流依次执行：

1. 使用 `actions/checkout@v4` 检出标签对应提交；
2. 使用 `docker/setup-qemu-action@v3` 提供跨架构模拟；
3. 使用 `docker/setup-buildx-action@v3` 配置 Buildx；
4. 使用 `docker/login-action@v3` 登录 GHCR；
5. 使用 `docker/metadata-action@v5` 生成镜像标签和 OCI labels；
6. 使用 `docker/build-push-action@v6` 构建并推送多架构镜像。

镜像构建参数为：

- context：仓库根目录；
- Dockerfile：`./Dockerfile`；
- platforms：`linux/amd64,linux/arm64`；
- tags：`ghcr.io/little6neko/comiclens:v0.1.0` 和 `ghcr.io/little6neko/comiclens:latest`；
- 缓存：GitHub Actions cache，写入使用 `mode=max`；
- `provenance: false` 和 `sbom: false`，与参考 workflow 保持一致。

若构建、登录或任一架构推送失败，整个 job 失败，不创建一个看似成功但缺少架构的正式发布结果。

## 版本统一

当前后端软件包、Python 模块和 Web 软件包已经是 `0.1.0`，但设置页前端版本常量仍为 `0.0.1`，Dockerfile 也没有镜像版本元数据。本次统一如下：

- `pyproject.toml`：保持 `0.1.0`；
- `app/__init__.py`：保持 `0.1.0`；
- `web/package.json` 和 `web/package-lock.json`：保持 `0.1.0`；
- `web/src/lib/version.ts`：从 `0.0.1` 更新为 `0.1.0`；
- Dockerfile runtime stage：新增默认值为 `0.1.0` 的 `VERSION` build argument；
- Dockerfile：新增 `org.opencontainers.image.version="${VERSION}"` OCI label。

设置页继续由前端版本常量渲染 `v0.1.0`。版本号不进入服务器设置，也不需要数据库迁移。

## README Docker 文档

README 在现有源码构建方式之前增加“Docker 镜像”快速安装章节。

### 镜像选择

文档同时展示：

- `ghcr.io/little6neko/comiclens:v0.1.0`：固定版本，适合稳定部署；
- `ghcr.io/little6neko/comiclens:latest`：跟随最新正式版本。

默认示例使用固定版本，避免重新部署时无意升级。说明镜像包含 `linux/amd64` 和 `linux/arm64`，Docker 会按主机架构选择对应镜像。

### 快速启动

主示例使用 `docker run`：

- 容器名为 `comiclens`；
- 映射宿主机 `8233` 到容器 `8233`；
- 设置 `--restart unless-stopped`；
- 将当前目录的 `data` 挂载到 `/app/data`，保留设置、缓存、历史和翻译结果；
- 默认不传 `COMICLENS_ACCESS_PASSWORD`，因此不显示密码页面；
- 需要密码时，展示添加 `-e COMICLENS_ACCESS_PASSWORD='...'` 的独立示例。

本地代理不是正式部署必需项，只在可选说明中指出可通过 `COMICLENS_PROXY_URL` 配置，不写入默认启动命令。

### 运行维护

README 增加以下常用操作：

- 查看容器状态；
- 跟随查看日志；
- 拉取指定版本或 `latest`；
- 停止并删除旧容器后，用相同挂载参数重新创建；
- 说明删除容器不会删除宿主机 `data` 目录中的持久数据；
- 若 GHCR 包尚未公开，提供使用具有 `read:packages` 权限的 token 登录 GHCR 的命令。

现有 Docker Compose 部分改为明确的“源码构建”入口，命令和 `docker-compose.yml` 保持不变。

## 发布顺序

完成实现和本地验证后按以下顺序发布：

1. 创建 release 提交 `chore: release v0.1.0`；
2. 将当前本地 `main` 的所有尚未推送提交推送到 `origin/main`；
3. 在 release 提交上创建轻量标签 `v0.1.0`；
4. 推送 `v0.1.0` 标签，触发 GitHub Actions；
5. 监控 workflow 直到成功或得到明确失败原因；
6. 验证 GHCR 的 `v0.1.0` 和 `latest` 标签，并检查 manifest 同时包含 amd64 与 arm64。

远端当前没有 `v0.1.0` 标签，因此不会覆盖已有发行标签。所有新提交继续使用：

- name：`little6neko`
- email：`little6carbon@163.com`

## 验证

发布前执行与改动风险相匹配的检查：

1. 检查 workflow YAML 语法和关键字段；
2. `npm run fmt:check`；
3. `npm run lint`；
4. `npm run build`；
5. 运行 Python 测试套件；
6. 若本机 Docker daemon 可用，执行本地镜像构建和健康检查；若不可用，以 GitHub Actions 的真实双架构构建作为最终容器验证；
7. 检查设置页显示 `v0.1.0`；
8. 检查 README 命令中的镜像名、端口、容器名、环境变量和数据路径；
9. 发布后检查 GitHub Actions 结果和 GHCR manifest 架构。

## 失败处理

- 本地测试失败时不创建或推送发布标签，先修复并重新验证；
- `main` 推送成功但标签 workflow 失败时，保留失败记录，修复后提交新改动；由于同名 Git 标签代表已发布版本，不在远端反复改写标签，必要时发布后续补丁版本；
- GHCR 包若默认为私有，镜像仍可通过 README 中的登录方式拉取；公开可见性需要在 GitHub Package 设置中单独确认，不由 workflow 擅自修改；
- 不删除现有本地 `data`、缓存或运行中的服务数据。

## 不在本次范围内

- Docker Hub、其他镜像仓库或自建 registry；
- 基于 `main`、pull request 或手动 dispatch 的发布；
- 自动生成 GitHub Release 或 changelog；
- 镜像签名、SBOM、provenance attestation；
- 自动修改 GHCR 包可见性；
- 将现有 `docker-compose.yml` 改为拉取 GHCR 镜像；
- OCR、翻译、缓存或阅读器功能调整。
