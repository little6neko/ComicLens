# 预先翻译提交等待优化设计

## 目标

点击“开始预先翻译”后，创建接口一旦成功返回，按钮立即结束“正在创建”状态并关闭弹窗。创建后的翻译概览和后台批次列表继续刷新，但刷新过程不再阻塞提交交互。

本次只优化前端成功后的等待时间。后端仍在创建批次前重新读取漫画目录，校验所选章节、确定从旧到新的处理顺序，并取得可信的章节标题；不改变批次调度、OCR、翻译或渲染逻辑。

## 方案比较

### A：本地立即更新并后台刷新（采用）

创建接口返回批次摘要后，立即把该摘要写入当前漫画的翻译概览缓存，显示批次已经建立；随后关闭弹窗、显示成功提示，并以不等待的方式刷新翻译概览和后台批次列表。

优点是界面立即一致，同时保留后台校准；不会出现按钮继续等待第二次漫画目录请求。代价是需要一小段明确的查询缓存更新逻辑。

### B：仅将刷新改为不等待

创建成功后直接关闭弹窗并在后台刷新，不主动更新缓存。改动最少，但批次按钮和页面状态可能短暂保留旧值，直到刷新完成。

### C：删除后端目录校验请求

让客户端提交章节标题和顺序，后端直接写库。虽然连创建接口本身的漫画目录等待也能消除，但客户端数据可能过期或被篡改，还会扩大请求模型与测试范围，因此本次不采用。

## 前端数据流

1. 用户提交已选择的章节 ID，按钮进入“正在创建”。
2. 后端完成现有目录校验和批次写入，返回 `CreateTranslationBatchResult`。
3. 有实际任务时，将响应中的 `batch` 写入 `translationOverview(comicId)` 查询缓存，保留缓存中的章节概览，仅替换批次摘要。
4. 立即显示成功提示并关闭预先翻译弹窗；此时 mutation 成功回调不返回待等待的 Promise，按钮等待状态随即结束。
5. 以后台方式失效并刷新 `translationOverview(comicId)` 与 `backgroundTranslationBatches`，用服务器最新状态校准本地缓存。

对于 `noWork` 响应，继续显示“无需处理”提示并关闭弹窗；同样不等待查询刷新。由于响应没有新批次，不向概览缓存写入批次对象。

## 错误处理

- 创建接口失败时保持现有行为：弹窗不关闭并显示错误提示。
- 已存在未结束批次时，继续刷新当前漫画概览并提示用户；该错误分支不是成功提交，不在本次改为乐观成功状态。
- 后台刷新失败不撤销已经成功创建的批次，也不重新打开弹窗；后续的一秒轮询或页面重访会再次同步状态。
- 本地缓存不存在时不构造不完整的翻译概览，仅启动后台刷新。

## 变更范围

只修改预先翻译弹窗的创建 mutation。后端 API、数据库模型、批次响应结构和调度器均不修改，也不触碰当前工作区内尚未提交的弹窗圆角及章节进度实现。

## 验证

- 格式化并运行前端静态检查和生产构建。
- 核对成功回调中不存在被 `await` 的查询失效操作。
- 核对有任务时本地概览立即包含返回的批次，原章节概览保持不变。
- 核对成功和 `noWork` 两条路径都立即关闭弹窗。
- 核对普通错误与“批次已存在”错误仍保留原有提示和恢复行为。
- 检查目标文件 diff 和 `git diff --check`，避免覆盖现有未提交改动。
