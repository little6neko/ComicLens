# ComicLens 全服务动态 OCR 并发设计

## 目标

让设置页现有的“OCR 并发”真正控制渐进分片流水线，同时保持默认值为 `1`。
调整后，用户可以在后台任务运行期间修改该设置，无需重启服务或重新创建翻译任务。

本次设计解决以下问题：

- 当前渐进流水线一次只完整处理一个分片，`ocr_concurrency` 虽传入 `OCRClient`，但单话任务
  实际始终只有一个 OCR 调用，因此修改设置几乎没有效果。
- 每个章节都会创建独立的 OCR 客户端；直接启用各客户端的信号量会使设置变成“每章上限”，
  多章并行时无法控制整个 ComicLens 服务提交给 PaddleOCR 的压力。
- OCR 通常远慢于 DeepL 与渲染，串行执行会让大部分时间消耗在等待云端 OCR。

成功标准是：当设置为 `N` 时，整个服务正常运行期间最多有 `N` 个由本进程管理的 PaddleOCR
任务处于提交或轮询阶段；OCR 结果可以乱序完成，但翻译、渲染、发布和阅读器展示仍严格遵循
分片的 `global_index`。

## 已确认的产品行为

1. OCR 并发默认保持 `1`，有效范围保持 `1–16`。
2. 该值是整个 ComicLens 服务共享的上限，而不是每个章节各自的上限。
3. 点击“保存全部设置”后立即应用到正在运行的后台任务，无需重启。
4. 从 `1` 调高到 `3` 时，调度器立即补充可用槽位；不等待当前慢 OCR 完成。
5. 从 `3` 调低到 `1` 时，不取消已经提交的任务；在活动数降到新上限以内前不再放行新任务。
6. 后续分片可以提前完成 OCR 并保存检查点，但翻译、渲染和发布仍按全局分片顺序串行执行。
7. 进度只保留一级。只有分片完成 OCR、翻译、渲染并发布后才计入
   `completed_segments`；仅 OCR 就绪不会增加进度。
8. 普通暂停、关闭实时翻译、强制停止和服务重启后都复用已保存的 OCR 结果或 `job_id`。
9. 本次不改变翻译并发、DeepL/DeepLX 行为、缓存语义或流水线语义指纹。

## 总体架构

`TranslationManager` 持有一个进程内共享、可动态调整大小的 OCR 限流器。所有渐进翻译
generation 的 OCR 客户端都使用这个限流器；不再由每个客户端独立决定实际并发数。

每个章节 worker 仍是独立的生产者—消费者流水线，但分片消费拆成两个边界清楚的阶段：

1. **OCR 预取阶段**：从已经切分并持久化的待处理分片中取任务，获得全局许可后提交或恢复
   PaddleOCR 作业，保存 OCR 原始响应及文字块检查点。
2. **顺序完成阶段**：只选择最小 `global_index` 的未完成分片，等待其 OCR 检查点就绪，随后
   串行执行翻译、渲染、缓存和发布。

源图获取与切片生产者不变。第一张源图切片写入数据库后，OCR 预取即可开始；后续源图发现的
分片继续动态追加到同一队列和总数。

限流器负责“何时允许一个 OCR 生命周期开始”，章节协调器负责“哪些分片值得预取”，
`SegmentRunner` 负责“如何完成一个阶段并落下可恢复检查点”。三者不互相读取内部状态。

## 动态全局限流器

新增一个专用的异步限流组件，至少维护：

- 当前配置上限 `limit`；
- 当前已获得许可的活动数 `active`；
- 等待许可的任务队列；
- 用于运行中调整上限并唤醒等待者的异步通知机制。

获得许可的范围覆盖一次 PaddleOCR 作业的完整本地生命周期：提交、持久化 `job_id`、轮询以及
取得结果。这样慢速 `pending/running` 作业也占用一个并发槽，而不是只限制瞬时 HTTP 请求。

调整规则如下：

- 增大上限后立即按差额唤醒等待者。
- 减小上限时保留现有许可；只有 `active < limit` 时才再次放行。
- 任务正常完成、失败或被取消时都必须在 `finally` 路径释放许可。
- 限流器只存在于当前进程；服务启动时从持久化设置读取初始值，默认 `1`。

等待者按进入共享限流器的顺序获得许可。章节协调器只维持一个有界预取窗口，不会把整章所有
分片一次性排进全局等待队列；一个任务完成后才补入后续分片。因此先启动的长章节不能预订
全部未来许可，新章节也不会被几十个尚未开始的分片长期阻塞。

PaddleOCR 当前没有取消远端作业的接口。普通暂停或强制停止取消本地轮询后，已经提交的远端
作业可能仍会继续运行；这类脱离本进程管理的作业无法计入即时并发保证。其 `job_id` 会保留，
恢复时重新获得全局许可后再查询，而不是直接重复提交。

## OCR 预取与顺序发布

章节协调器在下列条件同时满足时补充 OCR 预取任务：

- generation 未请求停止；
- 分片已经由准备生产者持久化；
- 分片尚无完整且有效的 `ocr_path` 与 `blocks_path` 检查点；
- 分片没有被另一个本地 OCR 协程占用；
- 预取窗口仍有空位。

预取协程先把该分片标为 `ocr`，再通过共享限流器执行 OCR。成功后原子保存
`ocr_path`、`blocks_path` 和 `ocr_job_id`，然后把分片恢复为可由顺序完成阶段选取的待处理状态。
“OCR 已就绪”由 `ocr_path` 与 `blocks_path` 均存在且缓存校验通过这一不变量表示，不新增表、
字段或数据库迁移。

顺序完成阶段始终检查最小 `global_index`：

- OCR 已就绪：直接读取文字块并进入翻译。
- OCR 正在执行：等待对应预取任务的通知。
- 尚未开始 OCR：确保它进入预取窗口并等待。
- OCR 已失败：保留分片失败状态并继续下一个全局分片。

后续分片即使先完成 OCR，也只能停留在检查点，不得提前调用翻译、渲染或发布。这样可以利用
PaddleOCR 并发，同时维持用户已经确认的逐片有序显示和稳定进度。

`SegmentRunner` 拆出独立的 OCR 阶段与翻译—渲染阶段；现有完整 `process` 入口可以组合两者，
供旧流水线和测试兼容使用。缓存命中时不占用 OCR 许可。

## 设置与运行时生效

设置页继续显示“OCR 并发”，范围 `1–16`，默认值 `1`。辅助说明改为：

> 全服务最多同时运行的 OCR 云端任务数，保存后立即生效。

设置仍属于服务器持久化配置，因此随“保存全部设置”提交。设置 API 成功写入数据库后，调用
`TranslationManager` 的运行时调整接口：

- 值未变化时不做额外调度；
- 值变化时调整共享限流器，并通知所有活动章节重新评估预取窗口；
- 调高时活动任务可以立即提交额外 OCR；
- 调低时不重启 generation、不清缓存，也不取消已有 OCR。

OCR 并发是运行资源设置，不进入 generation 的语义设置或指纹。修改它不能创建新的 generation，
也不能使已有 OCR、译文或译图缓存失效。

## 进度与可观测状态

现有一级进度含义保持不变：

```text
completed_segments / total_segments
```

`total_segments` 仍随准备生产者发现新分片而增长。`completed_segments` 只在译图发布成功后加一，
所以多个后续 OCR 提前完成时，进度不会跳过当前分片。设置页后台任务和阅读器无需增加第二条
OCR 进度，也不新增活动 OCR 数量指示器。

单个分片的持久化状态与路径仍可用于诊断当前阶段。日志应包含 generation、页码、分片序号和
OCR 作业标识，但不得输出 OCR Token、DeepL Key 或完整敏感响应。

## 暂停、停止与恢复

### 普通暂停或关闭实时翻译

- 立即停止补充新的 OCR 预取任务。
- 当前顺序分片允许完成 OCR、翻译、渲染和发布，然后 generation 进入 `paused`。
- 已经完成 OCR 的后续分片保留检查点。
- 后续仍在本地轮询的预取任务被取消，状态恢复为待处理；已经取得的 `job_id` 不清除。
- 再次开启时先复用有效 OCR 检查点；只有远端明确报告作业不存在或已失效时才重新提交。

### 强制停止

强制停止立即取消该 generation 的准备、OCR 预取和顺序完成协程。取消路径保留已提交的
`job_id` 和完整检查点，并将未完成状态恢复为可重试状态。PaddleOCR 远端作业不会被删除。

### 服务重启

启动恢复继续沿用现有规则，将中断时的 `ocr/translating/rendering` 状态恢复为待处理，保留所有
路径与 `job_id`。恢复后的 OCR 查询也必须先获得共享许可，因此多个章节同时恢复时仍服从当前
持久化的全服务上限。

## 错误处理

- 某个预取 OCR 失败时，只标记该分片失败并释放全局许可，不取消同章节其他 OCR。
- 失败位置继续显示现有的半屏失败占位及“重新翻译”按钮；失败分片不计入完成数。
- 后续 OCR 可以继续提前执行，但顺序完成阶段遇到失败片后才继续发布后续片。
- 点击失败分片重试时，优先恢复其 `job_id` 或复用 OCR 检查点，并与普通任务竞争同一个全局许可。
- 翻译、渲染或缓存失败沿用现有分片级错误语义，不影响 OCR 限流器。
- 设置保存失败时不调整内存限流器，保证运行值与持久化值一致。

## 翻译并发的现有边界

本次不修改 `translation_concurrency`。它默认是 `2`、有效范围为 `1–16`，并且是每个翻译
流水线的内部限制，不是全服务限制：

- DeepL 官方 API 会将当前分片的文字按每批最多 50 段、请求体小于 128 KiB 分批，再以该值
  限制批次请求；普通漫画分片通常只有一个批次。
- DeepLX 为当前分片的每个非空文字块发出独立请求，并以该值限制并发。
- 同一章节不同分片不会并发翻译；多个章节拥有独立翻译客户端，因此跨章节请求数可以累加。
- 运行中的翻译客户端不会因设置变化而重建；本设计不改变这一行为。

## 测试与验收

后端测试至少覆盖：

- 默认 OCR 并发为 `1`，API 拒绝 `1–16` 以外的值。
- 单章节设置为 `3` 时最多有 3 个 OCR 生命周期并行。
- 两个章节同时运行时，共享活动 OCR 数不会超过全服务上限。
- OCR 按反向顺序完成时，翻译、渲染、发布及 `completed_segments` 仍按 `global_index` 前进。
- 运行中从 `1` 调到 `3`，额外两个任务无需等待首个 OCR 完成即可启动。
- 运行中从 `3` 调到 `1`，已有三个任务不被取消，但释放前不再启动新任务。
- 普通暂停停止补充预取，完成当前顺序片，保留后续 OCR 检查点与 `job_id`。
- 强制停止取消本地协程并释放许可；重启恢复后复用检查点和远端作业。
- 单片 OCR 失败不会占死许可或取消其他预取；重试成功后仍按序发布。
- 缓存命中不调用 OCR，也不占用共享许可。
- 保存设置失败不改变运行中的并发上限。

回归验证包括完整 `pytest`、Ruff、前端 lint、TypeScript 检查和生产构建。实现不操作远程部署，
不清除现有缓存，不启动发布流程，也不修改版本号；这些动作只有在用户另行授权时执行。
