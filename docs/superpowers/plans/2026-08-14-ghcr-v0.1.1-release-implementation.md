# GHCR v0.1.1 发布实施计划

## 目标

按已确认的[发布设计](../specs/2026-08-14-ghcr-v0.1.1-release-design.md)，将当前已完成的
全服务动态 OCR 并发功能发布为 ComicLens `v0.1.1`。本次沿用现有 GHCR 多架构 workflow，
不创建 GitHub Release，不部署或重启远程服务器。

## 阶段 1：建立发布前基线

检查内容：

- 工作区没有未说明的用户改动；
- Git 作者为 `little6neko <little6carbon@163.com>`；
- remote 为 `git@github.com:little6neko/ComicLens.git`；
- 本地与远端均不存在 `v0.1.1`；
- `origin/main` 没有本地尚未整合的新提交；
- `.github/workflows/publish-image.yml` 仍只监听 `v*.*.*` 标签，并发布
  `linux/amd64,linux/arm64` 到 `ghcr.io/little6neko/comiclens`。

远端状态使用 `git fetch`、`git ls-remote` 或 GitHub 只读接口确认，不连接用户部署服务器。

## 阶段 2：统一 0.1.1 版本

涉及文件：

- `pyproject.toml`
- `app/__init__.py`
- `web/package.json`
- `web/package-lock.json`
- `web/src/lib/version.ts`
- `Dockerfile`
- `README.md`

实施内容：

- 将 Python 项目版本与 `__version__` 更新为 `0.1.1`；
- 将前端 package、lockfile 根包版本和设置页版本常量更新为 `0.1.1`；
- 将 Dockerfile 默认 `VERSION` build argument 更新为 `0.1.1`；
- 将 README 中固定镜像版本、升级变量和运行示例从 `v0.1.0` 更新为 `v0.1.1`；
- 不修改历史设计、实施记录中的 `v0.1.0`，也不把具体版本硬编码进 workflow。

验证：

- 所有运行时和包元数据版本一致；
- 非历史部署文档不再将 `v0.1.0` 作为当前安装版本；
- `git diff --check` 通过，改动范围仅包含计划内文件。

## 阶段 3：后端与前端发布门禁

后端执行：

- `.venv/bin/ruff check app tests`
- `.venv/bin/pytest -q`
- 读取 `app.__version__`、项目元数据、OpenAPI 和 `/health` 的版本结果。

前端执行：

- `npm run fmt:check`
- `npm run lint`
- `npm run build`
- `npx tsc --noEmit`

验证前端构建产物来自 `0.1.1` 版本常量。已经启动的本地 `0.1.0` 进程不因文件修改而热改版本，
发布期间不为此停止或重启服务。

## 阶段 4：本地容器验证

执行当前主机架构的本地 Docker build，并检查：

- 镜像构建成功；
- `org.opencontainers.image.version` label 为 `0.1.1`；
- 容器可启动且 `/health` 报告 `0.1.1`；
- 默认不设置 `COMICLENS_ACCESS_PASSWORD` 时仍可访问。

使用独立临时容器名、端口和临时数据目录，验证结束后只清理这些临时资源，不触碰现有测试服务、
正式数据或远程容器。本机仅验证当前架构，双架构产物由 GitHub Actions 验收。

## 阶段 5：创建 release commit

全部门禁通过后：

- 再次检查 diff、版本一致性和 workflow 未被修改；
- 只提交计划内版本与 README 文件；
- 使用指定作者创建 `chore: release v0.1.1`；
- 确认 release commit 内容和工作区干净。

任何门禁失败都先修复并重新运行相关完整检查，不在失败状态下创建 release commit 或标签。

## 阶段 6：推送 main 与标签

发布前重新获取远端状态，确认 `origin/main` 没有分叉且远端仍不存在 `v0.1.1`，然后：

1. 非强制推送本地 `main`；
2. 验证 `origin/main` 与 release commit 一致；
3. 在该 commit 创建轻量标签 `v0.1.1`；
4. 单独非强制推送 `v0.1.1`；
5. 验证远端标签与 release commit 一致。

不移动、覆盖或删除已经存在的远端标签。

## 阶段 7：跟踪 Action 与 GHCR 验收

使用 GitHub Actions/API 轮询由 `v0.1.1` 触发的 `Publish Docker image` run，直到成功或获得明确
失败结果。成功后检查：

- `ghcr.io/little6neko/comiclens:v0.1.1` 与 `latest` 均存在；
- 两个标签指向同一多架构索引摘要；
- manifest 包含 `linux/amd64` 和 `linux/arm64`；
- OCI version label 为 `0.1.1`，revision 为 release commit。

若 tag 推送后的 Action 失败，保留标签与 run 记录，不强制改写；报告具体失败点，再由后续补丁版本
修复。GHCR 短暂延迟时只等待并重复只读检查。

## 交付

- 发布设计、实施计划和 release 变更各自有独立可审计提交；
- `main`、`origin/main` 和 `v0.1.1` 指向 release commit；
- GitHub Action 成功，`v0.1.1` 与 `latest` 双架构镜像通过验收；
- 工作区干净，所有提交作者正确；
- 本地测试服务保持运行，远程部署没有任何变更。
