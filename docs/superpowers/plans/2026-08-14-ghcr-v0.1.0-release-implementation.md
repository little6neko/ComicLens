# GHCR 多架构镜像与 v0.1.0 发布实施计划

## 目标

按已确认的[发布设计](../specs/2026-08-14-ghcr-v0.1.0-release-design.md)，新增仅由版本标签触发的 GHCR 多架构镜像 workflow，统一应用和镜像版本为 `0.1.0`，完善 Docker 部署文档，并通过推送 `v0.1.0` 完成首个容器镜像发布。

## 阶段 1：建立标签触发的镜像发布流程

涉及文件：

- 新增 `.github/workflows/publish-image.yml`

实施内容：

- 仅监听符合 `v*.*.*` 的 Git tag push。
- 将 registry 和 image name 分别固定为 `ghcr.io` 与 `ghcr.io/little6neko/comiclens`。
- Job 使用 `contents: read` 和 `packages: write` 最小权限。
- 通过 checkout、QEMU、Buildx、GHCR login、metadata 和 build-push Actions 构建发布。
- 为每次标签发布生成原始 Git 标签和 `latest` 两个镜像标签。
- 构建 `linux/amd64` 与 `linux/arm64`，启用 GitHub Actions 构建缓存。
- 与 FileButler 参考流程一致，关闭 provenance 和 SBOM 输出。

验证：

- workflow 顶层触发条件不包含分支、pull request 或手动 dispatch。
- 镜像名、平台、权限、Dockerfile 路径和缓存字段与设计完全一致。
- 使用可用的 YAML/Actions 静态检查工具校验语法；若本机没有 actionlint，则同时通过 GitHub Actions 实际解析验证。

## 阶段 2：统一 v0.1.0 版本

涉及文件：

- 修改 `Dockerfile`
- 修改 `web/src/lib/version.ts`

实施内容：

- 在 Docker runtime stage 声明 `ARG VERSION=0.1.0`。
- 添加 `org.opencontainers.image.version="${VERSION}"` OCI label。
- 将设置页使用的 `APP_VERSION` 从 `0.0.1` 更新为 `0.1.0`。
- 复核 `pyproject.toml`、`app/__init__.py`、`web/package.json` 和 `web/package-lock.json` 已为 `0.1.0`，不做无意义重写。

验证：

- 仓库内所有项目版本入口一致为 `0.1.0`。
- 前端构建成功且设置页最终显示 `v0.1.0`。
- Dockerfile label 在默认构建时为 `0.1.0`，也允许未来通过 build argument 覆盖。

## 阶段 3：补充 Docker 安装与维护文档

涉及文件：

- 修改 `README.md`

实施内容：

- 在源码 Compose 部署之前增加预构建 GHCR 镜像章节。
- 说明 `v0.1.0`、`latest` 和 amd64/arm64 支持。
- 提供创建 `data` 目录及固定版本 `docker run` 命令。
- 单独展示设置 `COMICLENS_ACCESS_PASSWORD` 的启动命令，并明确不传时不启用密码界面。
- 提供状态、日志、停止、删除、重新创建和升级命令。
- 说明 `/app/data` 挂载负责持久化，删除容器不会删除宿主机数据。
- 提供私有 GHCR 包场景下使用 `read:packages` token 登录的命令。
- 将现有 Compose 标题明确为源码构建方式，保留其命令和行为。

验证：

- README 中所有镜像名均为 `ghcr.io/little6neko/comiclens`。
- 示例端口、容器名、数据路径和环境变量与 Dockerfile/应用配置一致。
- 默认示例不携带密码和本地代理；密码与代理均为显式可选项。
- 升级流程始终保留宿主机 `data` 目录。

## 阶段 4：本地质量检查

执行：

- `git diff --check`
- `.venv/bin/ruff check app tests`
- `.venv/bin/pytest -q`
- `cd web && npm run fmt:check`
- `cd web && npm run lint`
- `cd web && npm run build`
- 检查 workflow 中不存在占位值和错误镜像名。
- 检查版本文件输出一致。

容器验证：

- 若本机提供 Docker daemon，构建本地 `linux/amd64` 镜像并检查 OCI version label、启动和 `/health`。
- 若本机没有 Docker CLI 或 daemon，记录该限制，不安装或修改主机容器运行环境；以远端 GitHub Actions 的真实 Buildx 双架构构建作为最终容器验证。

任何本地检查失败都先修复并重新执行，不在失败状态下创建发布标签。

## 阶段 5：提交并发布 v0.1.0

实施内容：

- 只暂存 workflow、Dockerfile、前端版本和 README 改动。
- 使用 `little6neko <little6carbon@163.com>` 创建提交 `chore: release v0.1.0`。
- 确认工作区干净、远端仍不存在 `v0.1.0`。
- 将本地 `main` 推送到 SSH remote `git@github.com:little6neko/ComicLens.git`。
- 在 release commit 上创建轻量标签 `v0.1.0` 并推送。
- 不强推、不覆盖远端提交或标签。

验证：

- `origin/main` 指向 release commit。
- 远端 `refs/tags/v0.1.0` 指向同一 commit。
- GitHub Actions 出现由 tag push 触发的 `Publish Docker image` run。

## 阶段 6：跟踪 Action 与镜像验证

实施内容：

- 使用 GitHub API 或现有命令行能力轮询 workflow，直到成功或得到明确失败日志。
- 成功后检查 `v0.1.0` 与 `latest` 镜像标签。
- 检查多架构 manifest 至少包含 `linux/amd64` 和 `linux/arm64`。
- 若包未公开，记录需要 GitHub Package 可见性设置或 GHCR 登录，不擅自修改包权限。

失败处理：

- workflow 配置或代码导致失败时，修复后使用新的补丁版本发布，不改写已经推送的发行标签。
- 外部 GitHub/GHCR 故障时保留本地验证和远端 run 证据，报告明确状态与后续动作。

- 设计文档、实施计划和 release 实现均有独立、可审计提交。
- Git 提交者统一为 `little6neko <little6carbon@163.com>`。
- `main` 与 `v0.1.0` 已推送，GitHub Actions 和 GHCR 镜像已验证。
- 不修改或删除 ComicLens 的正式数据目录、OCR 缓存和翻译任务。
